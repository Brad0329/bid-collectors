# 승인 대기 점검 (Phase 종료용)

세션이 느리게 느껴질 때 줄여야 할 것은 대개 테스트가 아니라 **승인 대기**다.
이 스킬은 그것을 **추측이 아니라 트랜스크립트를 세어서** 처리한다.
(출처: kanadic 프로젝트에서 개발, 2026-08-19 — 본문의 실측 수치는 그 프로젝트 것이다.)

## 언제 부르는가

- **Phase 종료 시.** 단 **셸 호출이 100건 이상 쌓였을 때만** 의미가 있다 —
  짧은 구간의 노이즈에 규칙을 맞추면 규칙만 늘고 효과는 없다. 스크립트가 이 조건을 강제한다
  (미달이면 exit 2로 멈춘다. `--sessions N`으로 이전 세션을 합칠 수 있다).
- **사용자 호출 전용이다.** 설정을 바꾸는 일을 알아서 시작하지 않는다.

## 절차

### 0. 사용자에게 먼저 묻는다

**"무엇에 방해받았는가"를 사용자에게 먼저 묻는다.** 측정기 상위 항목이 가짜였던 실측이
두 번 있다(과대 계상·파이프 꼬리 오진). 반대로 사용자의 기억 한 줄(*"커밋 직전 8번, 전부
flutter test, 내가 판단할 건 하나도 없었다"*)이 진단을 완성했다 — **사람이 무엇에
방해받았는지는 사람만 안다.** 그걸 묻는 것이 트랜스크립트를 파는 것보다 빠르다.
받은 답을 `settings.local.json`의 최근 신규 항목과 대조하면 확정된다.

### 1. 측정

```bash
python scripts/measure_approvals.py
```

여러 세션을 합치려면 `--sessions 3`. 특정 세션은 `--session <ID 또는 경로>`.

**호출이 0건으로 나오면 '깨끗함'이 아니라 실패다** — 트랜스크립트 형식이 바뀌었거나 엉뚱한
파일을 본 것이다. 스크립트가 실패로 끝내니 그 메시지를 그대로 사용자에게 전한다.

### 2. 원인을 갈라서 읽는다 — 여기가 이 스킬의 핵심이다

**분류표의 상위 항목보다 `measure_wait.py`의 느린 순 상위를 먼저 본다** — 분류는 "자기 자신
(호출 형태)"을 과소 계상한 실사례가 두 번 있다(hanjadic 2026-08-20·08-29: 분류가 "형태 5회"라
할 때 실측 최대 원인이 전부 호출 형태였다).

보고서는 원인을 다섯 갈래로 나눈다. **처방이 서로 다르다**:

| 분류 | 처방 | 규칙을 넣는가 |
|---|---|---|
| **형태** (`cd <루트> &&` 등) | 호출 방식을 고친다. 반복되면 **PreToolUse 훅**으로 강제 | ✗ |
| **셸제어문** (`for`/`do`/`done`) | 셸 루프를 **파이썬으로** 옮긴다 | ✗ |
| **읽기전용** (grep·sed·wc…) | 인자가 매번 달라지는 자리면 **`settings.local.json`에** `명령 *`로 연다(슬래시 경로, Bash·PowerShell 양쪽). 아니면 호출 문자열을 고정한다. **`settings.json`의 allow는 효력이 없다** — 거기 넣지 않는다 | ○ (local에만) |
| **상태변경 — 비파괴** (git add/commit·build·install·pub get…) | **반복되면 연다** (2026-08-22 사용자 결정, CLAUDE.md '허용의 기준은 위험'). 단 먼저 **이미 열린 형태가 있는지** 본다 — 있으면 규칙이 아니라 습관 문제다 | ○ (local에만) |
| **상태변경 — 파괴** (삭제·reset --hard·force push·패키지 **추가**(새 의존성 — 잠금 파일대로 설치는 비파괴)·받은 실행물 실행) | **열지 않는다.** deny 유지. 호출 자체를 피한다 | ✗ |
| **판단필요** | 사람이 본다 | 사용자 확인 후 |

> **★ 이 표가 있는 이유**: 규칙만 늘려서는 안 줄어든다. kanadic 2026-08-19 실측에서 최대
> 원인(154회)은 **규칙이 아니라 내 호출 습관**이었고, hanmunstudy 2026-08-22에도 `git add -A`가
> 열려 있는데 `git add <경로>`로 불러 물었다. **규칙을 열기 전에 "열린 형태로 불렀나"를 본다.**
> 2026-08-22 이전 이 표는 "상태 변경은 무조건 안 연다"였다 — 그 원칙으로는 커밋·빌드마다
> 사용자가 불려 나오는 것을 구조적으로 못 없앴다(노하우 문서 '무엇을 열고 무엇을 남기나').

보고서의 `[시나리오] A/B/C`가 처방별 효과를 나눠 보여준다. **B(호출 형태만 고침)가 이미 크게
줄면 규칙을 넣을 이유가 그만큼 줄어든다.**

### 3. 처방을 사용자에게 제안하고 확인받는다

- 제안은 **규칙(비파괴)**과 **호출 습관/훅**으로 나눠서 낸다. 파괴적 명령은 제안 목록에
  넣지 않는다 — 필요하면 사용자가 먼저 말한다.
- 파일 조회로 쓴 필터(`← 파일 조회다` 표시)는 규칙이 아니라 **`Read`/`Grep`/`Glob` 도구로
  바꿀 자리**다. 규칙을 넣는 것은 파이프 뒷단(`flutter test | tail -3`)을 위해서다.

### 4. 반영

- 규칙: **`.claude/settings.local.json`의 `permissions.allow`에만** 넣는다 — `settings.json`의
  `allow`는 이 환경에서 효력이 없다(실측). 패턴에 역슬래시를 쓰지 않는다(슬래시 경로).
- 훅: 동봉 차단 훅은 **최대 5종**(`no_redundant_cd`(루트 대상 쓰는 `git -C` 포함)·`no_output_filter`·`no_inline_python`·
  `no_scratchpad_path` + 선택형 `no_targeted_flutter_test` — Flutter가 아니면 초기화 때 지운다.
  bid-collectors는 Flutter 자리에 `no_shell_file_write`(셸 `cat >`·`sed -i` 파일 쓰기, 2026-09-26)를 둔다).
  `session_context`는 차단이 아니라 SessionStart 주입 훅이라 이 점검 대상이 아니다. **개수를 외우지 말고
  `.claude/hooks/`의 실제 파일과 settings.json 등록 항목을 대조한다.** 등록은 **matcher
  `Bash|PowerShell` 한 블록**에 모아 둔다 — **한쪽 셸에만 걸면 반대쪽으로 그대로
  통과한다**(2026-08-22 실측). 경로의 `$CLAUDE_PROJECT_DIR`는 **환경에 따라 비기도 채워지기도
  한다** — 막히는 명령이 안 막히면 절대 경로(슬래시)로 바꾼다.
- 새 훅을 만들면 **반례까지 파이프 테스트하고 넣는다**(`no_redundant_cd`는 `cd app` 단독 호출을
  막으면 안 된다 — 테스트에 반례가 있다). deny 출력은 반드시 `hook_io.deny()`를 쓴다:
  직접 `json.dumps(..., ensure_ascii=False)`로 찍으면 **cp949 콘솔에서 죽어 훅이 통째로
  무력화된다**(2026-08-22에 4개 훅이 전부 이 상태였다).
- **등록 후 반드시 ① 막히는 명령 ② 정상 명령을 둘 다, Bash·PowerShell 양쪽에서 실제로 부른다.**
  통과하는 쪽만 보면 죽은 훅과 정상 훅의 증상이 완전히 같다.
- 습관: CLAUDE.md의 '작업 속도 규칙'에 한 줄. **다만 문서로 안 막히면 훅으로 옮긴다** —
  `cd` 함정은 문서에 두 곳이나 적혀 있었는데도 한 세션에서 154회 반복됐다.

### 5. 검증 — 스크립트를 고쳤다면

`python -m pytest tools_tests/test_measure_approvals.py`

이 분석기는 **죽지 않고 그럴듯하게 틀리는** 종류의 코드다(실제로 두 번 그랬다:
따옴표 안 파이프를 세어 건수가 부풀려짐 / `cd` 패턴 하나를 명령·조각에 같이 써서 "0건"이라는
거짓 결과). 로직을 건드렸으면 **그 경계를 재는 테스트를 넣거나 고치고, 변이를 하나 넣어 그 테스트가
실패하는 것을 본다** (변이는 테스트를 검증하는 수단 — CLAUDE.md '검증 강도' 사다리).

### 6. 커밋

```bash
git commit -F .commit_msg.txt
```

커밋 메시지에는 **원인별 건수와 시나리오 수치**를 남긴다. 다음에 같은 작업을 할 때
비교 기준이 된다.

### 7. ★ 마무리 — 두 가지를 반드시 한다

1. **규칙 반영을 그 자리에서 재검증한다** — **규칙은 즉시 걸린다**(2026-08-29 확정: 넣자마자
   같은 세션의 다음 보고서에서 사라짐). 실제로 묻던 명령으로 재검증하고, **판정은
   `settings.local.json`에 그 명령이 새로 적히는지로** 한다("한 번만 허용"은 안 남는다).
2. **보고서의 수치는 예측이지 실측이 아니다** — 양쪽으로 틀린 실사례가 있다(과대·과소).
   → **`scripts/measure_wait.py`로 벽시계를 재서 닫는다** (`--grep <명령>`으로 전후 비교).
   확인이 이 세션에서 안 끝났으면 인계 메모(`work_log/plan.md`)에 남긴다.
