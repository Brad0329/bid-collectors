# 노하우: 검증 (테스트가 실제로 무언가를 잡게 만드는 법)

> 출처: hanjadic 프로젝트 실측(2026-08). 스택 중립 — 어떤 프로젝트에도 적용된다.

## 테스트 자체를 검증하기

- **새 대조 테스트는 일부러 틀리게 해서 실패를 한 번 본다.** 통과만 보면 아무것도 검증하지
  않는 테스트를 통과로 착각한다. (틀린 스냅샷 주입→fail 확인, 정렬 뒤집기→409건 불일치로
  무의미한 테스트를 실제로 두 번 잡았다.)
- **변이(mutation) 확인은 두 단계 다 본다**: ① 변이가 실제로 적용됐는지 ② 테스트가 실패하는지.
  변이 스크립트의 대상 문자열이 안 맞아 파일이 그대로였는데 "통과"로 보인 실측이 있다.
  버그를 고쳤으면 회귀 테스트를 넣고, 고침을 되돌려 **그 테스트가** 실패하는 것을 한 번 본다
  (변이는 테스트를 검증하는 수단이다 — 테스트를 넣거나 고치지 않은 수정에는 붙이지 않는다,
  CLAUDE.md '검증 강도' 사다리 2026-09-05).
- **변이 확인의 비용을 줄이는 두 가지 (2026-09-18 사용자 결정, findchem·kanadic 트랜스크립트 실측)**:
  ① **되돌린 확인은 재실행이 아니라 diff로** — 변이를 되돌린 뒤 diff에 변이가 남아 있지 않으면 끝이고, 변이 전의
  통과 실행이 그대로 유효하다. ② **기존 단언의 기대값만 바꾼 것(상한 20→10)에는 변이를 붙이지 않는다** — 그 테스트가
  무언가를 잡는지는 처음 만들 때 봤다. 실측: 작은 커밋(코드 1~80줄) 12건에서 테스트 실행은 벽시계의 9%뿐이었지만,
  상수 하나 변경에 전체 실행이 3회(확인·변이·복원, 회당 약 55초) 붙어 한 줄 변경의 바닥이 약 3분이었다. 전체 실행을
  강제하는 스택(개별 실행을 훅으로 막는 Flutter)에서는 실행 횟수가 곧 비용이다.
- **변이는 한 번에 하나씩.** 같은 방어가 두 곳에 있으면 한쪽을 지워도 안 잡히고(헛통과 3건 전부
  이 유형), 변이 2개를 동시에 넣으면 하나가 다른 하나를 가려 엉뚱한 이유로 통과한다.
- **"안 깨진다"류 테스트는 무엇으로 깨짐을 감지하는지부터 검증한다.** 존재 확인(find류)은
  잘려도·가려져도 통과한다 — 실제 값(폭·크기·건수)을 직접 재는 방식이어야 잡는다.
  ("넘치지 않는다" 테스트가 실제 넘침 상태에서도 통과하고 있던 실사례.)
- **픽스처가 없어서 통과하는 테스트는 아무것도 검증하지 않는다.** 설정·환경 경로를 주입
  가능하게 만들어 양쪽 상태(있음/없음)에서 의도대로 도는지 확인한다.
- **회귀 테스트의 입력 데이터는 충돌·경계가 실제로 발생하는 값으로 고른다.** 값이 갈리는
  표본만 쓰면 값이 겹칠 때만 터지는 버그를 영영 못 잡는다(사용자가 본 증상이 재현 안 되던 실사례).

## 검증의 층 — 서로 대체가 안 된다

- **자동 테스트 / 코드 리뷰 / 사람 실테스트는 잡는 결함의 층이 다르다.**
  - 코드 리뷰 지적 6건 전부가 실패·경계 경로(null 크래시, 무한 로딩, 조용한 은닉)였다 —
    사람이 눌러 보는 검증은 정상 경로만 지나간다.
  - 반대로 자동 테스트 68건 통과 상태에서 실테스트가 원리적으로 자동으로 못 잡는 결함을 찾았다.
- **사용자 실테스트에는 "일부러 고장 상태를 만들어야 드러나는" 시나리오를 명시적으로 요청한다**
  (오프라인, 키 없음, 데이터 삭제 후 재시작 등). 정상 사용 중에는 통과 여부가 안 보인다.
- **악의적 입력 관점 점검은 정상 경로 테스트와 별개로 필요하다.** 자동 테스트 79건 통과
  상태에서 와일드카드 한 글자로 292KB 응답 증폭이 가능했다.
- **눈으로 확인한 것과 테스트가 지키는 것을 구분해 기록한다.** "사람 눈이 유일한 안전망"인
  자리를 명시해 둬야 그 화면을 고칠 때 다시 본다.

## 표시 변경은 사용자가 본다 (2026-09-18 사용자 결정, findchem발)

- **"사용자에게 보이는 방식"의 변경(화면 모양·배치·마우스 반응·색)은 사용자가 직접 보는 것으로 검증이 끝난다.**
  (목업 → "이대로" →) 구현 → 정적 분석 → push → 사용자 확인. 표시용 자동 테스트를 새로 만들지 않고, 전체 테스트는
  push 뒤 백그라운드로 한 번만(기존 테스트가 깨졌는지만).
- **목업은 모양을 AI가 골라야 할 때만 그린다 (2026-09-18 사용자 결정).** 사용자가 모양을 명확히 지시했으면("이 버튼을
  오른쪽으로", "글자색을 회색으로") 목업 없이 바로 구현한다 — 표시 변경은 되돌리기가 싸서 배포된 화면이 곧 목업이다.
  목업의 목적은 "AI 기본값이 디자인이 되는 것"을 막는 것이지 의식이 아니다. 지시에 빈 곳이 있어 AI가 채워야 하면
  (새 화면, 배치 미정, 선택지가 여럿) 그때 그린다.
- **실사례(findchem F-007 H·P 말풍선, 2026-09-18)**: 말풍선 표시 하나에 위젯 테스트 3건을 넣었더니 **전체 실행 8회**,
  실패 5회는 **전부 테스트 코드 자체의 결함**(마우스 좌표가 글자 경계에 떨어짐, 마우스 장치 중복 추가). 잡은 제품 결함 0건.
  사용자는 배포 뒤 한 번 보고 확인했다.
- **그래도 자동 테스트로 남기는 것 — 눈으로 안 보이는 동작.** 같은 날 유일하게 제품 결함을 잡은 테스트는 **복사 결과**
  테스트였다(화면으로는 안 보이는 동작). 복사 결과·건수·저장·로그·다른 화면에의 영향은 계속 테스트다.
- **비용의 정체는 실행 1회의 길이(실측 41~61초)가 아니라 반복 횟수였다.** 처음엔 "전체 실행이 3분이라 파일 지정 금지
  훅이 낡았다"고 봤으나 `measure_wait.py`로 재니 41~61초였다. 훅의 전제는 성립한다 — 고칠 것은 테스트를 만드는 판단이었다.

## 실제에 가깝게 검증하기

- **가짜(fake) 어댑터는 쿼리를 검증하지 못한다** — SQL을 해석하지 않는 가짜는 컬럼명이 틀려도
  통과한다. 실제 저장소에 한 번은 돌린다.
- **프로토콜 계층까지 실제 왕복으로 테스트한다.** 함수 직접 호출은 직렬화·등록·핸드셰이크를
  안 본다 — 정작 깨지는 곳이 그 계층이다.
- **헬스체크는 프로세스 생존이 아니라 핵심 자원을 실제로 읽는다** — 자원을 못 읽는 좀비 상태를
  정상으로 보고하지 않기 위해.

## 테스트 범위 조절 — 조용히 줄이지 않기

- **테스트 제외는 skip이 아니라 마커/deselect로** — "N deselected"가 항상 출력에 남는 방식을
  고른다. 조용히 줄지 않는 것이 핵심이고, 기능 중단 시 테스트를 지울 필요도 없어진다.
- **검증 생략에는 명시적 근거(의존 그래프)를 붙인다.** "이 변경이 그 테스트를 깨뜨릴 수 없는
  구조적 이유"(예: 해당 도구가 import하는 파일 목록)를 적고 생략한다 — 근거 없는 생략과 다르다.
- **기능이 화면·구조를 바꿔 옛 전제의 테스트가 성립 불가능해지면, 지우지 말고 기준을 살려 고친다.**
- **과하게 단정적인 기준은 대량 오탐을 만든다** — 기준을 좁히고 정당한 예외는 테스트에 명시
  등록한다(단정 하나가 400건 오탐을 낸 실사례).

## 디버깅 원칙

- **가설을 세웠으면 수정을 되돌려서 확인한 뒤 다음으로 간다.** 그럴듯한 가설이 실험으로
  반증되고 진범이 따로 잡힌 사례 — 되돌려 확인하는 절차가 헛수정을 막는다.
- **자동화 환경 자체가 상태를 바꿀 수 있다.** 검증이 이유 없이 실패하면 코드보다 먼저 현재
  URL·cwd·프로세스 상태를 찍는다 (파일 저장마다 브라우저가 이동해 검증이 깨지던 실사례).
- **원인 불명의 인증·설정 실패** → "지금 응답하는 게 내가 띄운 그 프로세스인가"부터 확인한다
  (죽지 않은 옛 서버가 포트를 쥐고 옛 설정으로 응답).
- **같은 원인의 버그를 고칠 때 다른 층에 같은 판정이 있는지 함께 본다.** 저장 쪽만 고치고
  화면 쪽을 안 고쳐, 문서에 함정으로 적혀 있었는데도 재발한 실사례.

## 측정 원칙

- **표본 2건은 실측이 아니다.** "실측으로 확인"이라 기록할 때 **표본 수와 확인 파라미터**를
  함께 적는다. 널뛰는 값이면 분포를 재고 꼬리를 본다. (표본 2건 결론이 두 번 틀렸다 —
  타임아웃 "30초 안"의 실분포는 5.1~44.0초였다.)
- **구현 착수 전 30초~30분의 측정이 설계를 바꾼다.** 사용자 제안도 재 보고 나서 구현한다.
- **틀린 것으로 밝혀진 기록은 조용히 고치지 말고 정정 사유(오독 경위)까지 남긴다** — 다음
  세션의 재오독을 막는다.
- **시간 데이터로 판별 불가능한 것은 볼 수 있는 사람에게 묻는 게 가장 싸다** — 표본을 더
  모아도 분포가 겹쳐 안 갈리던 것이 사용자의 한마디로 확정된 사례.
