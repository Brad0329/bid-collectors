# 노하우: 설계 원칙 (되돌리기 비싼 결정을 처음에 맞게)

> 출처: hanjadic 프로젝트 실측(2026-08). 스택 중립.

## 데이터 수명 — 가장 비싼 실수들

- **사용자 데이터를 빌드 산출물과 같은 파일에 두지 않는다.** 산출물은 재빌드·업데이트 때
  통째로 교체된다 — 저장·캐시는 별도 파일로.
- **기기/클라이언트에 누적되는 DB는 스키마 변경 시 반드시 마이그레이션을 함께 넣는다.**
  `CREATE TABLE IF NOT EXISTS`는 기존 테이블을 고치지 않는다 — 컬럼 추가 후 마이그레이션을
  빠뜨려 실기기에서 기능이 죽은 실사례(`no such column`, 예외는 조용히 삼켜졌다).
  통째로 교체되는 산출물 DB와 누적 DB는 규칙이 다르다.
  - 표준 절차(실기기 통과): **`PRAGMA table_info` 검사 → 없으면 `ADD COLUMN`.** 캐시는
    `DROP`으로 끝낼 수 있지만 사용자가 모아 둔 데이터는 그럴 수 없다 — 마이그레이션 결정은
    SCHEMA.md에 먼저 적고 사용자 확인 후 반영한다. **배포 전에 구버전 저장본을 실제로 읽어 본다** —
    단위 테스트는 새 코드가 만든 빈 DB로 돌아 전부 초록이었고, 이 사고는 옛 DB에서만 났다
    (CLAUDE.md 일반 트랙 검증 갈래의 출처, 2026-09-06).
  - **화면 요구가 바뀌면 컬럼이 따라온다** — 그것은 버그가 아니라 요구사항 변경이므로
    새 F-번호를 받는다(기존 번호의 "개정"으로 기록).
- **저장 시 "박제 vs 재조회"는 데이터 출처의 안정성으로 정한다.** 출처가 로컬(항상 재조회
  가능)이면 키만 저장해 개선이 자동 반영되게, 출처가 네트워크·휘발성 캐시면 저장 시점 값을
  박는다(캐시 참조는 사용자가 캐시를 비우는 순간 무너진다).
- **자연 키의 유일성은 실측으로 확인한다.** 중복 4건이 조용히 덮어써질 뻔한 실사례 —
  소스의 고유 코드로 PK를 바꿨다.
- **파싱해 저장하는 구조에는 버전 번호를 박는다.** 버전이 다른 행은 조용히 숨기지 말고
  "읽을 수 없음"으로 드러낸다 — 숨기면 사용자에겐 삭제로 보이고 재저장이 원본을 덮는다.
- **빈 상태로 저장하면 기존 데이터가 빈 것으로 덮인다** — 저장 전에 기존 데이터를 먼저
  불러오는 판정을 넣고, 그 판정을 순수 함수로 두어 테스트한다.

## 실패 처리

- **Silent failure 절대 금지** — 조용히 삼킨 예외는 "0건 처리"를 "정상 완료"로 둔갑시킨다.
- **부가 데이터(캐시 등) 읽기 실패가 본 기능을 죽이지 못하게 감싼다 — 단 로깅과 함께.**
  캐시 예외가 안 잡혀 버튼이 무반응이 된 실사례. 같은 지적을 받은 뒤 새 경로에 옮기는 것을
  또 잊었다 — 경로가 늘 때마다 전수 확인.
- **필수 자원이 없으면 조용히 뜨지 말고 시작 시점에 명시적으로 실패한다**(종료코드).
  조용히 뜨고 매번 "결과 없음"을 내는 것이 가장 비싼 실패 모드다.
- **조용한 절단 금지** — 결과를 상한으로 자르면 잘랐다는 사실과 전체 건수를 함께 돌려준다.
- **캐시 우선 시스템은 산출물 갱신 시 버전 올림을 잊으면 조용히 낡는다** — 가장 조용하고
  오래 가는 사고 유형. 검증할 때는 캐시버스터로 강제 갱신한다.

## 보안 기본값

- **보안은 opt-in이 아니라 기본값이 안전하게(fail-closed).** "설정하면 켜지는 인증"은 언젠가
  안 켜진 채 공개된다 — 토큰이 없거나 짧으면 아예 안 뜨게 한 실사례.
- **오류 응답에서 내부 정보(절대경로·사용자명)를 뺀다** — 밖으로는 상태만, 원인은 로그에만.
- 공개 엔드포인트 점검 목록(CLAUDE.md '보안 3층' ②에서 `/security-review`를 못 쓸 때 직접 대조하는
  실물): 패턴 검색 입력의 와일드카드 이스케이프(응답 증폭 방지) · 오류 메시지의 내부 정보 노출 ·
  인증 설정 부재 시 기동 거부 · 상수 시간 토큰 비교 · 로그에는 키 이름만 · 사용자 입력이 질의·셸·경로에
  문자열로 조합되는 곳 · 업로드 파일의 저장 위치·실행 가능 여부. (앞의 둘은 실제 취약점으로 발견·수정됐다.)
- **보안을 3층(코딩 규칙 / 범위 점검 / 공개 직전 전체 리뷰)으로 나눈 이유(2026-09-09)**: 종전 템플릿은
  "공개 Phase에 보안 점검 포함" 한 줄뿐이라 개발 중에는 아무것도 안 걸렸다. 그렇다고 "입력이 DB에 닿는
  커밋마다 점검"으로 걸면 초기 개발의 거의 모든 기능이 해당해, 검증 사다리에서 걷어낸 "주석 하나에도
  검증이 붙던" 문제를 보안으로 다시 만든다(사용자 지적). 결함 종류로 갈랐다: 쓰는 순간 정해지는 것
  (인젝션·fail-closed·오류 정보)은 규칙 + 정적 분석이면 초 단위라 층 ① / 판단이 필요한 것(인증·권한·
  업로드·결제·비밀정보·공개 표면)은 프로젝트당 몇 번뿐이라 분 단위 점검을 붙여도 싸서 층 ② /
  조합돼야 드러나는 것(권한 우회 경로·세션)은 공개 직전 전체 리뷰 층 ③. 인증 방식·공개 범위를 첫 외부
  입력 직전 게이트로 건 것은 '화면 방향' 게이트와 같은 이유 — 안 물으면 AI 기본값("인증 없음")이 정책이
  된다. 실측값은 없다 — 점검 자체보다 그 과정의 승인 대기가 비용일 가능성이 높고, 넣어 보고 재야 안다.

## 구조

- **테스트 가능성을 위한 최소 추상화는 YAGNI 위반이 아니다.** 어댑터 하나 없이는 실제
  저장소로 로직을 테스트할 방법 자체가 없었다.
- **의존성을 스스로 여는 조립 지점은 테스트가 가짜를 못 넣는다** — 프로덕션 생성자를 시험용으로
  뜯지 말고 판정을 순수 함수로 빼고, 조립 자체가 자동 검증 밖임을 로그에 명시한다.
- **외부 서비스는 인터페이스 뒤에 두어 갈아탈 자리를 남긴다 — 단 지금 필요한 만큼만.**
- **전송 계층은 뒤로 미루고 데이터 정합성부터 검증한다.** 전송은 나중에 바꿔 끼울 수 있지만
  데이터는 나중에 못 고친다 (실제로 한 줄 교체로 원격화된 사례).
- **산출물을 소비처로 복사하는 일은 산출물을 만드는 스크립트가 한다** — 사람이 기억하는
  절차는 언젠가 빠진다. 단 테스트용 임시 경로 빌드에서는 복사하지 않는 조건이 필요하다.
- **같은 값(라벨·상수)이 여러 파일에 흩어져 분기 기준이 되면, 일치 확인 테스트를 붙인다.**
  어긋나면 에러가 아니라 화면이 조용히 비는 종류의 결함이다.
- **exhaustive switch(등가물 포함)에 default를 넣지 않는다.** enum에 값을 더할 때 컴파일러가
  빠뜨린 곳을 전부 짚어 주는 안전망이다 — default를 넣는 순간 사라진다.

## UI·상태

- **누를 수 있는지 판정은 그리는 시점에 한다.** 콜백 안에서 판정하면 "눌리는 것처럼 보이는데
  반응 없는" UI가 된다 — 같은 결함을 두 번 만들었고 두 번 다 테스트가 잡았다(눈으로는 못 잡는다).
- **작업·진행 상태는 (대상, 종류) 쌍으로 식별한다.** 서로 다른 작업의 대상 문자열이 우연히
  같아질 수 있다 — 종류 없이 판정한 모든 곳이 오작동한다.
- **설정 저장값은 enum 이름이 아니라 안정된 ID로.** 알 수 없는 저장값은 기본값으로 되돌리되
  로그를 남긴다(조용히 바꾸지 않는다).
- **사용자 설정이 기본값과 같으면 저장하지 않는다** — 그래야 기본값 개선을 사용자가 따라온다.
  저장하면 옛 기본값이 "사용자가 고른 값"인 척 굳는다.
- **결과 범위를 닫는 것이 기본값이다.** 재귀적으로 파고드는 기능(결과에서 또 같은 기능)은
  필요해지면 여는 쪽이 싸다.

## 범위 결정

- **수록 범위를 좁게 시작하면 "없다" 경험이 학습된 불신을 만든다.** 좁혀서 아끼는 것과
  불신 비용을 비교해 정한다 — 넓히는 건 쉽지만 그 사이의 불신이 더 비싸다.
- **일괄 제외/삭제 전에 대체재의 존재를 건별로 확인한다.** 무조건 지우면 대체 없는 항목이
  조용히 사라진다 (범위 삭제 대신 건별 확인으로 정보 손실 0을 확인한 사례).
- **손으로 만든 데이터에는 자동 검증을 붙인다.** 수작업 141쌍 중 5쌍이 틀렸고(방향 반대 포함)
  참조 데이터 존재 검사가 전부 걸렀다. 수작업 범위 자체는 오탐률·검증 비용 대비 실사용
  빈도로 한정한다.
