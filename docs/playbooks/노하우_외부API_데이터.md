# 노하우: 외부 API·데이터 소스 (문서를 믿지 말고 실측한다)

> 출처: hanjadic 프로젝트 실측(2026-08). 스택 중립.

## 착수 전 실측

- **문서·기억 속의 필드명·모델명·엔드포인트를 믿지 않는다.** 원본을 열어 실제 이름과 건수를
  확인한다. (기획안의 필드 2개가 원본에 존재하지 않았고, 기억 속 모델명 2개도 존재하지
  않았다 — 목록 조회 API로 확인해 잡았다.)
- **커버리지도 실측한다.** 대체 필드가 있어도 커버리지가 기대의 일부일 수 있다
  (기대 1,800건 중 128건이던 실사례 — 보정 데이터가 필요해졌다).
- **"실측으로 확인"이라 기록할 때 표본 수와 확인 파라미터를 함께 적는다.** 파라미터 하나가
  최소값 미만이라 오류 응답을 빈 응답으로 오독하고, 그 위에 설계가 얹힌 실사례. 기록에
  파라미터가 있어야 나중에 재현·반증이 된다.

## 응답 처리

- **200이 성공이 아닐 수 있다 — 상태 코드가 아니라 본문을 확인한다.** 키가 틀려도 HTTP 200에
  본문에만 오류 코드가 오는 API가 실재한다 — 키 오류가 "결과 없음"으로 둔갑한다.
- **정렬이 호출마다 다를 수 있다** — 화면 안정성이 필요하면 안정 키로 재정렬한다.
- **부분일치를 주는 API는 정확일치 필터 없이 쓰면 엉뚱한 것이 올라간다** (더 긴 표제어·파생어
  혼입 실측).
- **확인한 형식만 파싱하고 원문(raw)은 항상 보존한다** — 형식이 바뀌거나 파싱이 실패해도
  원문이 있으면 복구된다.
- **HTTP 타임아웃은 헤더 수신만이 아니라 본문 읽기에도 건다.** "헤더만 보내고 멈춘 서버"를
  로컬로 재현해 검증한 사례 — 응답이 커지면 헤더 뒤에서 무한 대기가 실제로 가능하다.

## 파일 데이터 소스

- **파서는 처음부터 1:N을 전제로 짠다.** 키당 1행 가정으로 커버리지를 99.1%로 오측정한
  실사례 — 전 행 수집 시 100%였다.
- **파일 앞부분 샘플만 보고 형식을 단정하지 않는다.** 30만 행 중 대상이 2.7만 행뿐인데
  무관한 행들이 앞머리에 몰려 있어 형식을 오해하기 쉬웠다.
- **번들하는 외부 데이터의 라이선스 고지는 모든 배포 형태에 필요하다** — 개인용이라도
  스토어에 올리는 순간 문제가 된다.

## 네트워크와 핵심 기능의 분리

- **네트워크 기능이 추가돼도 앱 시작·핵심 기능은 네트워크를 기다리지 않게 초기화를 분리한다.**
  핵심 → 부가 순. 부가 초기화 실패 시 그 사실을 알리되 핵심 기능이 정상임을 명시한다(빈 화면 금지).
- **오류 원인 판정에 순서를 명시한다.** 초기화 실패를 "키 없음"보다 먼저 판정하지 않으면
  사용자가 멀쩡한 키를 다시 넣는다.
- **무료 조회는 미리 해 캐시에 남기면 사용자 체감 시점의 네트워크를 0으로 만들 수 있다** —
  비용을 앞당겨 치르는 설계.
