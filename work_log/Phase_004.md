# Phase 004 — v1.1 신뢰성 (2026-09-23)

## ① 실패한 접근과 원인

- **보조금24 서버 필터가 v1.0부터 무력했다** — 절단 보고를 넣고 실 API로 돌리자 `보조금24 1일`이 50페이지 상한에
  걸려 "전체 10,498건 중 5,000건"을 보고했다. 처음엔 cutoff 자정 절삭(이번 항목 6)의 부작용을 의심했으나, 1일·30일
  필터가 같은 matchCount(10,498/전체 10,933)를 내는 것으로 필터 자체가 안 먹는다는 게 드러났다. 원인: `수정일시` 값은
  `YYYYMMDDHHMMSS`인데 `YYYY-MM-DD HH:MM:SS`로 보냈다 — odcloud `cond[...::GTE]`는 문자열 비교라 `'0' > '-'`로 거의 전부 통과.
  미래 날짜(2099)만 0건이라 "필터가 동작한다"로 보였던 것이 함정. → 형식을 API 값과 맞춰 1일 24·7일 213·30일 1,406건.
  REQUIREMENTS F-005는 "서버 필터"라고 적혀 있었지만 아무도 건수를 재지 않았다 — **v1.0 소비자는 매 수집마다 5,000건(무관한
  서비스 대부분)을 받고 있었다.** 조용한 절단을 보고하게 만든 것이 곧바로 숨은 결함을 드러낸 사례.
- **통합 테스트 기대값을 안 고쳐 게이트 1차 불합격** — 통합 테스트는 한도 절약으로 `max_pages=1`을 쓰는데 `errors == []`를
  단언하고 있었다. 단위 테스트(-m "not integration")만 돌리고 커밋해 놓쳤다. 동작을 바꾸면 통합 테스트의 기대도 같은 커밋에서 본다.
- **변이 하나를 잘못 설계** — `collect()`에서 `_mask`를 무력화하는 변이는 이미 `_fetch` 안에서 가려진 뒤라 아무것도 안 바꿨다.
  마스킹은 수집기 단·`collect()` 단 이중이므로 변이는 공통 함수(`mask_secret`)를 무력화해야 잡힌다.

## ② 다음 세션이 알아야 할 것

- **GenericScraper `pagination=""`는 1페이지만** 요청하도록 바꿨다(v1.0은 같은 URL을 max_pages번 받았고 중복 제거가 숨겼다).
  그 상태로 절단 보고를 넣으면 모든 단일 페이지 사이트가 "잘렸다"고 거짓 보고한다 — 두 변경은 한 몸이다.
- **GenericScraper 절단 판정**: 마지막 페이지까지 다 받았고 그 페이지에 cutoff 이전 행이 없을 때만 보고한다. 전체 건수를 알 수 없어
  메시지에 "다음 페이지 미확인"으로 적는다. 기본 `max_pages=3`이라 BidWatch 정기 수집에서 is_partial이 자주 뜰 수 있다 —
  소비자가 이것을 "장애"로 취급하지 않게 bidwatch 세션에 알린다(plan.md 실테스트 대기).
- **마스킹은 이중**(수집기에서 만들 때 + `collect()`에서 한 번 더) — 로그에도 키가 안 남게 하려면 수집기 단이 필요하고,
  errors로 새는 것은 `collect()` 단이 최종 방어. 새 수집기는 `self._mask(...)`로 메시지를 만든다.
- 나라장터 `_request_with_retry`는 이제 None 대신 `RuntimeError`(`from None` — 원래 예외가 키 든 URL을 품고 있어 연결 끊음).
- 실 API 표본(2026-09-23, 정상 키): 나라장터 용역 1일 1,021건/11p · 기업마당 1일 46건(max_pages=1) · K-Startup 7일 35건 ·
  보조금24 1일 24건·7일 213건 · 중소벤처기업부 7일 9건. 잘못된 키는 data.go.kr이 **403**(resultCode가 아니라 HTTP)으로 돌려준다.
