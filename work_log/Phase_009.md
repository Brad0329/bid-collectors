# Phase 009 — 자체조달 기관 수집기 4종 (v1.4.0)

## ① 실패한 접근과 원인

- **d2b 경쟁 3종의 차수를 `g2bPblancOdr`로 잡음 → 취소공고가 원공고에 합쳐짐**: 조사 보고의 "g2bPblancNo = 연도+공고번호+판단번호, 100% 일치"를
  보고 `g2bPblancNo`·`g2bPblancOdr`를 한 쌍의 출처 합성키로 보고 계약안에 넣었다(사용자 확인까지 받음). 첫 실호출(7일)에서 `total_fetched` 418 ≠
  중복 제거 후 409 — `collect()`의 bid_no 중복 제거가 **서로 다른 공고 9건을 조용히 지웠다**. 겹친 행의 차이를 찍어 보니 `pblancOdr`(1→2)·`pblancSe`
  (정상→취소)만 다르고 `g2bPblancOdr`는 01 그대로. → 차수 = `pblancOdr`(5종 공통)로 정정, 모양(`D2B-{구분}-{키}-{차수}`)은 유지(배포 전).
  교훈: 조사의 "고유키 중복 0"은 **그 표본에서 취소·정정 행이 없었을 뿐**일 수 있다. 새 수집기 실측에서는 `total_fetched == total_after_dedup`을
  반드시 본다(`scripts/_tmp/real_institutions.py`가 둘을 함께 찍는다) — 다르면 합쳐진 행의 차이 필드를 찍는다(`d2b_dups.py`).
- **d2b 수의 2종 start_date = `ntatPlanDate`로 잡음 → 미래 날짜**: 이름("협상계획일자")만 보고 공고일 대용으로 썼는데 실측 범위가 9/28~2027-05-06 —
  앞으로의 협상 예정일이었다. 공고일 필드가 없으므로 None(원문은 extra).
- **수자원을 50건 페이지로 받음 → 서버 정렬 불안정으로 조용한 누락**: 조사의 "51KB 초과 시 빈 본문"을 피하려고 50건씩 나눴더니 실호출 14일
  154행 → 중복 제거 후 150건. 겹친 행은 필드가 완전히 같았고(1·2페이지에 같은 행) totalCount는 그대로 — **겹친 수만큼 다른 공고가 빠진 것**이다
  (조사 때 "100행 1·2페이지 겹침 0"은 그날 정렬이 우연히 안정적이었을 뿐). XML로 바꿔 보려 했으나 XML이 JSON보다 크다(용역 142건 XML은 빈 본문,
  JSON 53KB는 됨). → 한 페이지 1000건으로 전량을 먼저 받고, 빈 본문이면 50건씩 나누되 겹친 행 수를 errors로 알린다(`scripts/_tmp/kwater_dups.py`·`kwater_onepage.py`).
  빈 본문 경계는 51KB가 아니다(53KB 성공) — 정확한 값은 모른다.
- **변이 H7(헬퍼 키 마스킹 제거)이 수집기 테스트로 안 잡힘**: `collect()`가 errors를 한 번 더 마스킹하기 때문. 헬퍼의 마스킹은 **로그로 새는 것**을 막는
  몫이라 헬퍼 테스트(`test_datagokr::test_second_page_failure_keeps_first`)가 잡는다.
